# Syncing with Empyreal

The station maps are built from the Empyreal source, `~/dev/empyreal`. When
the maintainer pushes, run this routine to bring the maps up to date. The
source is only ever read. Never edit it.

## The routine

1. `git -C ~/dev/empyreal pull`
2. `npm run build:data`
3. Read the report to John: what changed, and what needs a human.
4. `npm test`, then look at the preview (`dev/preview.html`).
5. Commit as `data: sync with empyreal <sha>`, with the generated files and
   `data/sync-report.json`.

The build prints the report as short text, one line per list that has
anything in it, or `nothing needs you`. The same report is written to
`data/sync-report.json`.

Flags, all optional:

| Flag | Default |
| --- | --- |
| `--source DIR` | `~/dev/empyreal` |
| `--tweaks DIR` | `data/tweaks` |
| `--out DIR` | `ui/data` |
| `--report PATH` | `data/sync-report.json` |

## Generated files are not edited by hand

Every `.js` file in `ui/data/` starts with
`// GENERATED by npm run build:data from empyreal <sha>. Do not edit.`
`data/sync-report.json` is JSON, so it has no comment. It carries the commit
as `commit`. A hand edit is lost at the next build. To change how a map
looks, change a tweak file. To change what a map says, it has to change in
the Empyreal source.

`ui/data/places.js` is generated too. It imports every place's file and
exports the index and the data by id, so a new place needs no code change.

The build never writes tweak files. It reads them.

## The report

Each list is empty when there is nothing to say.

- `newPlaces`: areas that are new in the source, each with the builder that
  will draw it. Look at the preview. Add a tweak file if it needs colours.
- `removedPlaces`: places we had that the source no longer has. Their
  generated files are gone. Delete the tweak file by hand if it is now dead.
- `noBuilder`: new areas no builder knows how to draw (no layout, not a
  decks box, drum or town). Nothing was made for them. Tell John.
- `rooms.added`, `rooms.removed`: rooms that appeared or went, per place. A
  removed room that comes back under another id, with the same address (else
  the same name), is listed under `renamed` instead.
- `rooms.renamed`: `from` and `to` ids. Tweak keys that use the old id are
  now orphans. Rename them in the tweak file.
- `exits.added`, `exits.removed`: exits that now lead somewhere else, or
  appeared or went, on rooms that exist before and after. Exits of added and
  removed rooms are not listed. Check the preview for a layout that moved.
- `unplaced`: rooms the builder could not place, or that a drum's tweak does
  not list. Add them under `place` (or `drum.rooms`) in the place's tweak.
- `orphans`: tweak keys that name a room the place does not have, as
  `place: key`. Fix the id, or delete the key.
- `droppedFlags`, `unknownFields`: room flags and source fields the map
  drops on purpose, listed by name with the places they occur in, the first
  time a name appears only. Nothing is wrong. Decide if the map should use
  it. `knownDroppedFlags` and `knownUnknownFields` remember every name seen,
  so it is not reported twice.

`commit` is the source commit the build read. Use it in the commit message.

## Tweak files

The look is in `data/tweaks/<place>.json`, one file per place, with the
place's id as its name. Room keys are the local ids, without the area prefix
(`gallery`, not `orrin.gallery`). The colours are names from
`data/tweaks/palette.json` (`concourse`, `residential`, `hydroponics`,
`commons`, `offices`, `midring`, `industrial`, `docks`, `hub`). An unknown
key or palette name makes the build fail with the file and the key.

The top-level keys:

- `like`: another place's tweak to start from. This file's keys win. Each
  halt that looks like Orrin says `"like": "orrin"`. Lamorna adds its own
  `paint` and a mast on top.
- `paint`: room to colour. `"market": "concourse"`.
- `paintDistricts`: district to colour, for towns. Zennor has
  `"old-town": "commons"`.
- `fixtures`: things drawn on a decks or drum plan. Each has a `type`:
  - `blister`: `{ "type": "blister", "room": "gallery" }`
  - `cradle`: `{ "type": "cradle", "side": -1, "deck": 3, "hw": 0.34, "hh": 0.3, "len": 0.7 }`
  - `mast`: `{ "type": "mast", "side": -1.25, "frame": 3.35, "height": 1.65 }`
    (Lamorna's)
  - `drum-cradle`: `{ "type": "drum-cradle", "hour": -0.3, "z": -12, "hw": 8, "h": 20, "hl": 11 }`
    (Wenna's)
- `place`: a room's position, where the source gives none or the build
  cannot find one. T.I.S.S. has
  `"place": { "transfer": { "x": 0, "y": -1, "z": 3 } }`.
- `drum`: a drum's layout. `rooms` places each room by `x`, `y`, `z`,
  `hour`, `band` and `terrain`, and there are also `axis` and `way`. See
  `wenna.json`.
- `town`: a town's furniture. `root`, `uphill`, `ground`, `gate`, `wells`,
  `river` and `scarp`. See `zennor.json`.
- `wheel`: reserved for wheel stations. Empty in stage 1.

`scripts/source/tweaks.mjs` lists every allowed key.

## Adding a place

When `newPlaces` names one, the build has already drawn it plainly, and
`places.js` already lists it. Add `data/tweaks/<place>.json` with a `like`
and any `paint` you want, run `npm run build:data` again, and look at the
preview.

If the place is in `noBuilder` instead, nothing was drawn. A drum needs a
`drum` section and a town a `town` section in its tweak file.
