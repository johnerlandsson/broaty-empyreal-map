# Syncing with Empyreal

The station maps are built from the Empyreal source, `~/dev/empyreal`. When
the maintainer pushes, run this routine to bring the maps up to date. The
source is only ever read. Never edit it.

## The routine

1. `git -C ~/dev/empyreal pull`
2. `npm run build:data`
3. Read the report to John: what changed, and what needs a human.
4. `npm test`, then look at the preview (`dev/preview.html`). A golden render
   (`tests/golden/`) that fails for a place the report names is expected: the
   source changed it. Check that place in `dev/preview.html`, then
   `GOLDEN_RECORD=1 npx vitest run tests/golden` and commit the goldens with
   the sync. A new place fails until its golden is recorded the same way. A
   golden that fails for a place the report does not name is a real problem:
   stop and find out why before recording anything.
5. Commit as `data: sync with empyreal <sha>`, with the generated files and
   `data/sync-report.json`.

The build prints the report as short text, one line per list that has
anything in it, or `nothing needs you`. The same report is written to
`data/sync-report.json`.

The report is what changed since the last commit: in a git checkout the
build compares with the files and the report as `HEAD` has them, so running
it again before you commit gives the same report. Outside git it compares
with the files on disk.

The build stops with one message, and writes nothing, when the source has no
area files or when it would remove every place the map has. Either means the
checkout is partial.

Flags, all optional:

| Flag | Default |
| --- | --- |
| `--source DIR` | `~/dev/empyreal` |
| `--tweaks DIR` | `data/tweaks` |
| `--out DIR` | `ui/data` |
| `--report PATH` | `data/sync-report.json` |

## Generated files are not edited by hand

Every `.js` file in `ui/data/` starts with
`// GENERATED by npm run build:data from empyreal <sha>. Do not edit.`
`data/sync-report.json` is JSON, so it has no comment. It carries the commit
as `commit`. A hand edit is lost at the next build. To change how a map
looks, change a tweak file. To change what a map says, it has to change in
the Empyreal source.

`ui/data/places.js` is generated too. It imports every place's file and
exports the index and the data by id, so a new place needs no code change.

The build never writes tweak files. It reads them.

## The report

Each list is empty when there is nothing to say.

- `newPlaces`: areas that are new in the source, each with the builder that
  will draw it. Look at the preview. Add a tweak file if it needs colours.
- `removedPlaces`: places we had that the source no longer has. Their
  generated files are gone. Delete the tweak file by hand if it is now dead.
- `noBuilder`: new areas no builder knows how to draw (no layout, not a
  decks box, drum or town). Nothing was made for them. Tell John.
- `rooms.added`, `rooms.removed`: rooms that appeared or went, per place. A
  removed room that comes back under another id, with the same address (else
  the same name), is listed under `renamed` instead.
- `rooms.renamed`: `from` and `to` ids. Tweak keys that use the old id are
  now orphans. Rename them in the tweak file.
- `exits.added`, `exits.removed`: exits that now lead somewhere else, or
  appeared or went, on rooms that exist before and after. Exits of added and
  removed rooms are not listed. Check the preview for a layout that moved.
- `unplaced`: rooms the builder could not place, or that a drum's tweak does
  not list. Add them under `place` (or `drum.rooms`) in the place's tweak.
- `orphans`: tweak keys that name a room the place does not have, as
  `place: key`. Fix the id, or delete the key.
- `droppedFlags`, `unknownFields`: room flags and source fields the map
  drops on purpose, listed by name with the places they occur in, the first
  time a name appears only. A field inside a car, an exit, a layout or a
  district is named by its dotted path, such as `car.perStop` or
  `exits.*.hidden`. Nothing is wrong. Decide if the map should use
  it. `knownDroppedFlags` and `knownUnknownFields` remember every name seen,
  so it is not reported twice.

`commit` is the source commit the build read. Use it in the commit message.

## Tweak files

The look is in `data/tweaks/<place>.json`, one file per place, with the
place's id as its name. Room keys are the local ids, without the area prefix
(`gallery`, not `orrin.gallery`). The colours are names from
`data/tweaks/palette.json` (`concourse`, `residential`, `hydroponics`,
`commons`, `offices`, `midring`, `industrial`, `docks`, `hub`). An unknown
key or palette name makes the build fail with the file and the key.

The top-level keys:

- `like`: another place's tweak to start from. This file's keys win. Each
  halt that looks like Orrin says `"like": "orrin"`. Lamorna adds its own
  `paint` and a mast on top.
- `paint`: room to colour. `"market": "concourse"`.
- `paintDistricts`: district to colour, for towns. Zennor has
  `"old-town": "commons"`.
- `fixtures`: things drawn on a decks or drum plan. Each has a `type`:
  - `blister`: `{ "type": "blister", "room": "gallery" }`
  - `cradle`: `{ "type": "cradle", "side": -1, "deck": 3, "hw": 0.34, "hh": 0.3, "len": 0.7 }`
  - `mast`: `{ "type": "mast", "side": -1.25, "frame": 3.35, "height": 1.65 }`
    (Lamorna's)
  - `drum-cradle`: `{ "type": "drum-cradle", "hour": -0.3, "z": -12, "hw": 8, "h": 20, "hl": 11 }`
    (Wenna's)
- `footprints`: room to the shape it is drawn in, on a decks plan. See
  "Footprints" below.
- `hull`: deck to the path of its hull, on a decks plan. See "The hull" below.
- `view`: how a place is seen: `cutaway` and `camera`. See "View" below.
- `place`: a wheel room's position, where the build cannot place it from
  its address. It applies only to wheels. T.I.S.S. has
  `"place": { "transfer": { "x": 0, "y": -1, "z": 3 } }`.
- `drum`: a drum's layout. `rooms` places each room by `x`, `y`, `z`,
  `hour`, `band` and `terrain`, and there are also `axis` and `way`. See
  `wenna.json`.
- `town`: a town's furniture. `root`, `uphill`, `ground`, `gate`, `wells`,
  `river` and `scarp`. See `zennor.json`.
- `wheel`: reserved for wheel stations. Empty in stage 1.

`scripts/source/tweaks.mjs` lists every allowed key.

No tweak file shipped with the plugin uses `footprints`, `hull` or `view`
yet. Every place looks as it did before them.

### Footprints

A footprint is how a room is drawn, never where it is. It applies to decks
places only; on any other place the build stops with an error. The units are cells: a room's cell centre is at (side, frame),
and the cell spans 0.5 either way. x is the side (starboard +) and y is the
frame (fore +). A room with no footprint is one plain cell.

```json
"footprints": {
  "exchange": { "span": { "port": 1 }, "corners": "rounded", "r": 0.3 },
  "gallery": { "outline": [[-0.5, -0.5], [0.5, -0.5], [0.5, 0.3], [0, 0.6], [-0.5, 0.3]] }
}
```

- `span`: how far the room reaches past its own cell, in cells, 0 or more,
  by `fore`, `aft`, `port` and `starboard`. Any of the four may be left out.
- `corners`: `square` (the default), `rounded` or `cut` (chamfered).
- `r`: the radius or chamfer of a rounded or cut corner, in cells. It is 0 or
  more and under half the footprint's narrower side. The default is 0.2.
- `outline`: a list of three or more `[x, y]` points, each within -1.5 to 1.5
  of the cell's centre. It replaces `span` and `corners`. It must not cross
  itself.

The build stops, naming the tweak file and the two room ids
(`footprints: A and B overlap. Nothing written`), when two rooms on the same
deck have footprints that overlap. Touching edges are fine. Rooms neither of
which has a footprint are left to the source.

The mockup of the options is `docs/maps/reference/footprints-options.png`.

### The hull

`hull` applies to decks places only; on any other place the build stops with
an error.

By default a deck's hull is the box its cells fill. `hull` replaces that with
a closed path, one per deck, keyed by deck number, in the same cell units as
footprints. A point is `[x, y]`, or `[x, y, r]` to round that corner with
radius `r` cells (more than 0). This is Orrin Station's, from
`docs/maps/reference/hull-path-mockup.html`, a cross round its rooms on
Deck 3 with the nose chamfered 0.3, and an L on Deck 2 with one rounded
corner, all 0.12 cells outside the cells:

```json
"hull": {
  "3": [
    [-0.62, 0.38], [0.62, 0.38], [0.62, 1.38], [1.62, 1.38], [1.62, 2.62], [0.62, 2.62],
    [0.62, 3.32], [0.32, 3.62], [-0.32, 3.62], [-0.62, 3.32],
    [-0.62, 2.62], [-1.62, 2.62], [-1.62, 1.38], [-0.62, 1.38]
  ],
  "2": [[-0.62, 0.38], [0.62, 0.38], [0.62, 2.62], [-1.62, 2.62, 0.35], [-1.62, 1.38], [-0.62, 1.38]]
}
```

A deck with no entry keeps its box. Through `like`, a deck's path is
inherited; `"3": null` puts it back to the box. A path with fewer than three
points, one that crosses itself (also once its corners are rounded), or a
rounded corner too big for its edges makes the build fail with the file and
deck. So does a key that is not a deck number. A deck the place has no rooms
on is listed in the report as an orphan (`hull.<deck>`).

The build also stops, naming the deck and the room or fixture, when a path
cuts through a room (each room is checked brought in 0.1 cells, the drawn
room box), when a cradle's side is not on the path of its deck, or when a
mast is not inside the top deck's path. A cradle sits at the path's nose on
its side.

The mockup of the options is `docs/maps/reference/hull-path-options.png`.

### View

`view` is how a place is seen. Any place may have one.

```json
"view": { "cutaway": "ghost-above", "camera": { "yaw": 16, "pitch": 38, "zoom": 1 } }
```

- `cutaway`: what the model does with the decks above yours. `off` draws it
  whole. `hide-above` lifts them off and leaves a dashed outline. `ghost-above`
  draws them as a faint ghost. The default is `hide-above` on a decks place
  and `off` on every other kind.
- `camera`: the overview's home angle, `yaw` and `pitch` in degrees, and
  `zoom`, more than 0, where 1 frames the whole model and 2 is twice as
  close. All three are needed. The default is yaw 16, pitch 38, zoom 1.

### Not yet

These are in the design (`docs/superpowers/specs/2026-10-26-map-data-from-source-design.md`,
"The hull") but not built. For now the build stops with an error if a tweak
for a wheel, drum or town has a `hull` or `footprints`:

- hull paths on wheels and drums. A wheel's path will be per ring, drawn on
  the unrolled ring plan that repeats as you pan, with the spokes, hub and
  spine as numbers in the `wheel` section.
- footprints on wheels, drums and towns.
- a cutaway on a wheel.

## Adding a place

When `newPlaces` names one, the build has already drawn it plainly, and
`places.js` already lists it. Add `data/tweaks/<place>.json` with a `like`
and any `paint` you want, run `npm run build:data` again, and look at the
preview. Then record its golden render, as in step 4.

If the place is in `noBuilder` instead, nothing was drawn. A drum needs a
`drum` section and a town a `town` section in its tweak file.
